# Правила проекта

## Git и GitHub

- Основная ветка: `master`.
- Перед реализацией создавать issue с описанием задачи и критериями готовности.
- Для каждого issue создавать отдельную ветку и отдельный PR.
- В случае логической громоздкости реализации на одно issue можно создавать несколько PR. Для каждого PR использовать отдельную рабочую ветку.
- Названия веток: `<номер-issue>-<название>`.
- Формат коммитов: `[#<номер-issue>] [label-ы] ...`. Использовать метки соответствующего issue; например, `[#9] [enhancement] Add PR history checks`.
- В описании PR указывать изменения, результаты проверок и `Closes #<номер-issue>`.
- Если одно issue реализуется несколькими PR, в промежуточных PR указывать `Refs #<номер-issue>`, а `Closes #<номер-issue>` — в PR, который завершает задачу.
- Изменения в `master` вносить через PR.
- Сливать PR способом Rebase and merge после успешного CI.
- Перед финальными проверками выполнять `git fetch origin` и `git rebase origin/master`. Ветка PR должна включать актуальный `master` и не содержать merge-коммитов; для слияния обязательны успешные checks `CI`, `Tests (ubuntu-latest)` и `Tests (windows-latest)`.
- После вливания PR удалять его рабочую ветку локально и на GitHub.
- Изменения в PR дробить на небольшие логические коммиты.
- Способ разработки — test driven development (TDD). Перед написанием кода фичи сделать отдельный коммит с тестами для этой фичи. Сначала убедиться, что новые тесты не проходят из-за отсутствующей реализации, затем реализовать фичу и добиться прохождения тестов.

## Rust

- Перед PR запускать:

  ```text
  cargo fmt --check
  cargo clippy --locked --all-targets -- -D warnings
  cargo test --locked --all-targets
  ```

- При изменении поведения обновлять документацию.
- Добавлять тесты для нового поведения и исправляемых ошибок.
- Все Rust-тесты хранить в `tests`, а не в `src`: интеграционные тесты — в `tests/*.rs`, тесты внутренних функций — в `tests/unit`, проверяемые примеры документации — в `tests/docs`. В `src` допускается только подключение тестовых модулей через `#[cfg(test)]` и `#[path]`, а примеров — через `#[doc = include_str!(...)]`.
- В собственном Rust-коде запрещены `unsafe`-блоки и функции; запрет `unsafe_code = "forbid"` должен сохраняться в Cargo.
- Документировать публичный API и непримитивные внутренние функции через `///`: назначение, существенные ограничения и ошибки. Примеры документации должны проходить `cargo test --locked --doc`.
- Делить большие модули по обязанностям и выносить повторяемую логику в общие функции или отдельные модули.

## Релизы и CI

- Использовать один workflow `.github/workflows/ci.yml` для проверок и выпуска.
- Все тестовые цели Cargo и примеры документации запускать в отдельной job `tests` на Windows и Linux; CI-скрипты из `tests/ci` проверять в этой job на Linux. Итоговый check `CI` не должен проходить при ошибке, отмене или пропуске тестовой job.
- Обычные коммиты, PR и слияния в `master` запускают проверки без сборки установщика.
- Создавать теги версий и публиковать релизы только по явной просьбе пользователя. Самостоятельно выпускать релизы запрещено.
- Для запрошенного релиза использовать отдельный тег `v<версия>`, соответствующий `Cargo.toml` и указывающий на коммит из истории `master`.
- Сборку, тестирование и публикацию установщика запускать вручную через input `release_tag` workflow `CI` после явной просьбы пользователя. Создание тега само по себе не запускает выпуск.
- Инструкции разработки и выпуска хранить в `docs/development.md`; README предназначен для установки и использования программы.

## Общение

- Описания issue и PR писать на русском.
- Названия PR писать на английском.
- Формат названия PR: `[#<номер issue>] <реализуемая фича>`.
- Сообщения коммитов писать на английском.
